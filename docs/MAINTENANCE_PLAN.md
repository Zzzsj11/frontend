# 长期维护清单

> 目标：在当前版本完成线上验收后，按阶段推进，把项目从“可用”继续打磨到“可长期维护、可扩展、可回滚”。

## 现阶段原则

- 先保证线上稳定运行，再推进结构性优化。
- 所有变更优先保持向后兼容，避免影响已验证的用户旅程。
- 任何会影响数据、鉴权、媒体存储或部署方式的改动，必须先补测试，再上线。
- 新增能力尽量配置化，不把逻辑硬编码散落在组件和路由里。

## 阶段一：线上验收后立即做

1. 固化生产配置
- 拆分本地、测试、生产三套环境变量。
- 生产环境单独维护 `docker-compose.prod.yml` 或等价部署文件。
- 所有密钥、TOS 配置、模型 Key、数据库密码都移出仓库。

2. 收紧部署入口
- 只保留 HTTPS 对外访问。
- HTTP 统一跳转到 HTTPS。
- 证书签发和自动续期保留在服务器侧，形成可复用脚本。

3. 确认数据库与 Redis 访问策略
- 默认不对公网开放数据库和 Redis。
- 如需人工调试，优先通过 SSH 隧道访问。
- 如果必须开放端口，必须限制白名单 IP。

4. 归档当前测试资产
- 固化真实 E2E 的输入、截图和测试说明。
- 保留 ASS 分镜与通用分镜的完整回归样本。
- 记录这版上线后的基线结果，方便后续比较。

## 阶段二：稳定性与可观测性

1. 日志与告警
- 后端 API 错误日志入库后，补查询和导出能力。
- 接入外部错误追踪服务，汇总异常栈和请求上下文。
- 为关键流程补告警：登录失败、生成失败、TOS 上传失败、导出失败。

2. 指标监控
- 记录接口耗时、成功率、失败原因分布。
- 记录生成任务数量、并发量、重试次数。
- 记录 Token 消耗、图片/视频生成次数和导出次数。

3. 数据备份
- PostgreSQL 做定期备份。
- 设计恢复演练流程，确保能从备份恢复到可用状态。
- Redis 保持可重建，不把它当成唯一事实来源。

## 阶段三：构建与依赖治理

1. 锁定构建环境
- 固定 Python、Node、Docker 基础镜像版本。
- 固定 pip 源或私有镜像源。
- 为后端依赖补充锁定文件，减少线上线下差异。

2. 复现性检查
- 本地、CI、服务器三处构建结果保持一致。
- 每次升级依赖前先在测试环境验证。
- 避免未经验证的自动升级。

3. 代码结构收敛
- 把模型 ID、提示词模板、媒体约束等配置集中管理。
- 减少组件中出现重复常量。
- 为后续模型扩展保留统一入口。

## 阶段四：功能扩展前的技术债整理

1. 模型扩展
- 把当前固定的 `Img2`、`sd2.0` 扩展成可配置列表。
- 增加模型切换后的兼容测试。
- 更新弹框、API、数据库和提示词模板的联动逻辑。

2. 用户与权限
- 如有更复杂协作需求，再补角色权限分级。
- 为管理员、普通用户、只读账号分别定义能力边界。
- 审计重要操作，尤其是删除、导出和媒体覆盖。

3. 媒体与导出
- 所有媒体统一走 TOS。
- 导出包、封面、首帧、生成视频保持一致的存储策略。
- 为大文件和失败重试准备更清晰的用户提示。

## 阶段五：迭代节奏建议

- 每次改动只聚焦一个主题。
- 每次上线前都跑一次对应用户旅程的完整回归。
- 每次模型、部署或权限改动后，都更新这份清单。
- 清单中每一项都应该有对应的代码、测试或脚本入口。

## 建议的后续推进顺序

1. 线上验收完成后，先做生产配置分层。
2. 再做依赖锁定和构建复现。
3. 然后补监控、日志和告警。
4. 最后再推进模型扩展和权限细化。
