# 提示词运营闭环演示手册

> 面向业务方与管理员的实操指南：用一支 MV 的生成过程，完整演示
> 「业务方生成视频 → 发现问题 → 反馈需求 → 管理员调整提示词 → 重新生成 → 满足新需求」闭环。
> 对应功能：系统提示词管理后台（草稿 / 试渲染 / 发布 / 回滚）。

## 1. 角色与前置准备

| 角色   | 职责                                       | 需要准备                                                                           |
| ------ | ------------------------------------------ | ---------------------------------------------------------------------------------- |
| 业务方 | 走正常生成旅程，验收产出质量，提出问题反馈 | 普通账号；一首带 ASS 字幕的歌曲（可用曲库歌曲，如编号 10012204）；1–2 个系统数字人 |
| 管理员 | 接收反馈，在管理后台编辑并发布提示词       | 具有 admin 角色的账号                                                              |

通用约定：

- 演示使用 **ASS 分镜** 主线（覆盖环节最全）；通用分镜的差异在第 6 节单独说明。
- 提示词修改**只对之后新生成的内容生效**，已产出的大纲/提示词/视频不会自动变化，
  业务方必须重新生成对应环节才能验证效果。
- 发布后全链路约 60 秒内生效（运行时缓存 TTL，发布会主动失效缓存）。

## 2. 提示词地图：问题出在哪一环，就改哪一个

| 生成旅程环节                | 产出物                                                                  | 对应提示词 key                                                                                |
| --------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 大纲第 1 轮：全歌划场景     | globalVisual、locations、scenePlan、motifs                              | `ass.scene_plan.system` / `ass.scene_plan.rules`                                              |
| 大纲第 2 轮：场景内逐镜     | 每镜 shotType、characterAction、emotionalFocus、cameraPurpose、motifIds | `ass.scene_shots.system` / `ass.scene_shots.rules`                                            |
| 逐镜画面提示词              | scenePrompt、shotPrompt（直接喂给图/视频模型）                          | `storyboard_line.system` / `storyboard_line.requirements` / `storyboard_line.role_constraint` |
| 全局策略（注入 storyBible） | 人物策略、负向约束、地点规则、风格优先级                                | `story_bible.ass.*`                                                                           |
| 通用分镜大纲（无歌词）      | 通用 MV 逐镜大纲                                                        | `general.story_outline.system` / `general.story_outline.rules`                                |
| 数字人身份参考卡            | 1024x1536 竖版单人正面头肩大头照                                        | `portrait.digital_human_ref`（image 引擎）                                                    |

## 3. 演示剧本（三幕主线）

### 幕一：场景单一 → 改 `ass.scene_plan.rules`

**业务方操作**

1. 新建任务：上传 ASS 字幕文件，选择歌曲与数字人，提交解析。
2. 点击「生成大纲」，等待两轮 LLM 完成。
3. 浏览 scenePlan：整支 MV 像是在同一个地方拍的，副歌也没有视觉变化。

**反馈话术（示例）**

> 「整支 MV 场景太单一，主歌副歌看起来差不多，希望相邻场景差异更大、副歌更有冲击力。」

**管理员改法**
打开管理后台 → 提示词面板 → `ass.scene_plan.rules` → 新建草稿，将第 3 条规则由
"至少两项不同"收紧为"至少三项不同 + 副歌强对比"。完整内容（可直接粘贴）：

```json
[
  "按主歌、副歌、桥段等音乐结构与叙事阶段划分场景，每句歌词必须且只能属于一个场景。",
  "lineStart、lineEnd 是歌词句序号（从 0 开始、含端点）；场景按时间顺序连续推进，完整覆盖全部歌词，不得重叠或遗漏。",
  "相邻场景的视觉基调必须有明显差异（地点、光线、色彩、氛围至少三项明显不同），副歌场景必须使用与主歌形成强对比的色调与光线，避免观众审美疲劳。",
  "structuralSegments 说明的前奏、间奏、尾奏是系统拆出的无人空镜素材，可作为场景切换的天然节点，不需要你为它们分配行号。",
  "先确定全片统一的视觉基调 globalVisual，再让每个场景在其框架内变化。"
]
```

试渲染 → 发布（操作细节见第 4 节）。

**验证**：业务方**重新生成大纲**，对比新旧 scenePlan：相邻场景 visualTone/mood 差异应明显变大。

> 备注：场景*数量*由程序按歌词句数决定（模板变量 `{{expected_scenes}}`），提示词改不了数字；
> 若反馈是"场景切得太粗/太细"，在 `ass.scene_plan.system` 中补充倾向性引导
> （如"快节奏歌曲倾向更细粒度切分场景"）。

### 幕二：运镜单调、动作与时长不匹配 → 改 `storyboard_line.requirements`

**业务方操作**

1. 大纲确认后，对若干镜头执行「生成提示词」。
2. 查看 shotPrompt：几乎都是固定机位；8 秒的镜头动作描述 5 秒就演完了。

**反馈话术（示例）**

> 「镜头全是固定机位太死板；而且动作时长和镜头时长对不上，希望运镜有变化、动作铺满全程。」

**管理员改法**
`storyboard_line.requirements` → 新建草稿，在 JSON 数组**末尾追加两条**（其余保持不变）：

```json
"相邻镜头的运镜方式不得重复，推、拉、摇、移、跟至少交替使用两种以上。",
"动作设计必须铺满 plannedDuration 全程，结尾预留 0.5 秒定帧，不得提前演完。"
```

试渲染（确认 `jsonError` 为空）→ 发布。

**验证**：业务方对**同一条分镜重新生成提示词**（无需重跑大纲），新 shotPrompt 中应出现
运镜方式描述，且动作节奏与 plannedDuration 匹配。

> 备注：`storyboard_line.*` 处于 KV-cache 前缀稳定区，发布后既有任务的前缀缓存会失效，
> 短期 LLM 时延/成本略升，属正常现象。

### 幕三：画面出现字幕/水印 → 改 `story_bible.ass.negative_constraints`

**业务方操作**

1. 用生成的 scenePrompt/shotPrompt 生成场景图与视频片段。
2. 播放视频：角落有类似平台水印的文字。

**反馈话术（示例）**

> 「生成的视频角落有水印样文字，需要明确禁止一切文字标识。」

**管理员改法**
`story_bible.ass.negative_constraints` → 新建草稿，补充两条（完整内容可直接粘贴）：

```json
[
  "无字幕",
  "无水印",
  "无 Logo",
  "无平台标识",
  "无文字弹幕",
  "不得出现未指定人物",
  "不得改变人物服装与身份"
]
```

注意「无字幕」「无水印」是该模板的**必含片段**，删除会导致发布被拦截（422）。

**验证**：业务方**重新生成提示词 + 重新生成视频**（负向约束经 storyBible 注入提示词，
两级都要重跑），新视频中文字标识应消失。

## 4. 管理员后台操作指引

每个模板的编辑发布流程一致：

1. **新建草稿**：在模板详情页基于当前版本编辑，保存为新草稿（版本号自动 +1）。
   草稿不做强制校验，可暂存半成品。
2. **试渲染**：提交前先看试渲染报告，三项必须为空才允许发布：
   - `missingFragments`：缺少必含安全片段（防注入语、"纯 JSON" 等）；
   - `undeclaredVariables`：使用了未声明的 `{{变量}}`（代码不会为它传值）；
   - `jsonError`：JSON 模板必须是合法的字符串数组。
3. **发布**：发布后旧版本自动转为 archived，全链路 60 秒内生效；
   每次草稿与发布都会写入审计日志（操作人、版本、变更备注）。
4. **回滚**：效果不满意时，选择符合**当前 DB 必含片段和变量声明**的旧版本重新发布。
   published / archived 版本永久保留不可删除，仅草稿可删。新头肩照规则下的历史多视图版本不能直接回滚发布，见第 4.2 节。

**两条红线**

- 必含安全片段不能删（各模板要求不同，编辑页有标注，发布接口强制校验）；
- 不能新增 `{{变量}}`：模板变量由代码注入，新增变量代码不会传值，发布直接 422。

### 4.1 数字人身份参考卡：单张正面头肩大头照

`portrait.digital_human_ref` 不再生成左侧大头、右侧多视图参考卡，也不再需要系统人物的版式参考图。

- **输入**：上传/重新生成时仅发送一张人物身份参考图；无图 AI 创建按 `description` 生成人物。唯一模板变量仍为 `{{extra}}`，由后端将非空 `description` 拼成「角色描述：…。」；空描述不填人物名。`style` 仅为资产分类，不拼入画面风格。
- **输出**：1024x1536 竖版、单人正面、人物居中，仅头部、肩部和少量上胸，完整保留头顶和发型。纯白无图案圆领短袖 T 恤、中性灰纯色背景、棚拍柔光，不佩戴饰品、不持道具。
- **身份**：保留五官、脸型、肤色、年龄感和发型；儿童不得成人化，卡通保留卡通特征，不强行真人化。有参考图时以图中身份为准；描述中的衣着、职业、年代、场景不能覆盖统一造型。
- **禁止**：全身/侧面/背面像、多人、拼图、多视图、原服装/职业/场景背景继承、边框、文字、Logo、水印。
- **下游**：`storyboard_line.requirements` 和 `story_bible.general.character_policy` 仍明确忽略参考卡原服装、灰背景、排版（包括历史多视图）、职业和年代暗示；头肩照不能提供全身身体比例。剧情服装继续按大纲及季节规则决定，未选人物时仍可自由选角。

新版 `required_fragments` 为以下逐字片段（不再绑定第一张或第二张参考图）：

```text
单人正面头肩大头照
五官、脸型、肤色、年龄感和发型
无身份参考图时
不得成人化
纯白无图案圆领短袖T恤
不佩戴饰品
中性灰
棚拍柔光
禁止继承
无边框、无文字、无Logo、无水印
```

必含片段是最小文本校验，不等同于完整语义或出图质量校验。请以当前部署代码的 `defaultContent` 为新模板基线，保留完整身份与构图规则。尺寸还须由生成请求的 `size` 参数落实，不能只改提示词。

### 4.2 发布要求：代码默认值不等于存量 DB 已升级

核查依据：`backend/app/prompts/registry.py`、`backend/app/seed.py::seed_prompts`、`backend/app/admin.py` 的提示词接口。

- 运行时读取顺序为 **进程内缓存（60 秒 TTL）→ DB 当前 published 版本 → 内置 defaults**。内容有效的旧 DB 版本不会因 defaults 改动或缺少新必含片段而自动失效；运行时不重新做必含片段校验。
- seed 仅创建缺失 key 的模板与 v1；已有 key（包括软删除记录）整条跳过，不覆盖文案、名称、说明、变量或 `required_fragments`。全新环境完成正常迁移后首次 seed 可直接得到新模板；存量环境重启或重跑 seed 都不构成升级。
- 详情中的 `defaultContent` 来自当前代码，但 `requiredFragments`、`variables` 来自 DB。试渲染、发布与回滚均按 DB 元数据校验；现有管理接口只能管理内容版本，没有修改这些元数据的接口。
- 历史迁移 `e9b4c6d8f102_neutral_identity_reference_prompts.py` 曾发布多视图文案，只切换内容版本，未更新 `required_fragments`；后续 `f2a6d9c4b701_publish_season_first_wardrobe_rules.py` 也不会升级本次头肩照元数据。不能假定现有数据库与 defaults 相同，更不能重跑或修改历史迁移。

**存量环境实施顺序（前向迁移已提供；本次未执行真实 DB 迁移或部署，实际部署须另行确认）：**

1. 管理员先读取并留存上述三个 key 的当前版本、正文与模板元数据，检查线上实际 `requiredFragments`。为业务定制文案保留差异及回退方案。
2. **已提供 `backend/migrations/versions/d6f2a8c1e903_headshot_prompt_metadata.py`**，承接 `b3f7a1c5e902`。仅更新未软删 `portrait.digital_human_ref` 的 `name`、`description`、`variables`、`required_fragments` 和 `updated_at`：基础元数据对齐新版 defaults，精确替换旧「第一张参考图」「第二张参考图」规则，保留额外自定义必含安全片段及变量。迁移冻结常量，不导入运行时 defaults；不新建模板，不改 `current_version_id` 或任何版本正文、发布状态，不改 seed、管理权限或重复迁移 PPIO 字段。提供迁移不等于存量环境已升级；禁止手工直改数据库或给新正文硬塞旧片段绕过卡口。
3. 实际部署须另行确认后，通过版本化镜像及 `scripts/deploy.sh` 的正常发布流程部署代码与经批准的迁移；协调前端仅一张身份图、无图 AI 创建与结构化 `size=1024x1536` 同步上线。部署前完成 `make preflight` 和对应无费用 Playwright 验证。
4. 核对管理详情：必含片段包含第 4.1 节列表和保留的额外运营约束，`extra` 说明不再含画面风格。**仍需基于新版 `defaultContent` 发布三个模板：`portrait.digital_human_ref`、`storyboard_line.requirements`、`story_bible.general.character_policy`**。逐一创建草稿、合并完整身份/历史卡安全语义及无关运营定制，满足额外必含约束，再试渲染并发布；迁移不会代替发布正文。portrait 试渲染需提供 `extra`（空串也可），并按各模板声明提供其他所需变量，确保 `missingVariables`、`undeclaredVariables`、`missingFragments`、`jsonError` 均为空。**只升级元数据或只发布正文都不完整。**
5. 发布只立即失效处理该请求进程的缓存；其他 API/Worker 进程至多等待 60 秒 TTL，必要时在安全排空后重启。通过无费用 `/api/generations/images/portrait-prompt` 核对最终提示词；用 mock 测试核对无图/单图生成请求快照和下游规则，不为验收主动生成付费图片。
6. 已生成资产、大纲和工单请求快照不会被重写，历史多视图仍按 identity-only 规则使用；不要自动重发旧工单。回滚发布也会执行新片段校验，旧多视图正文可能返回 422，优先发布符合新规则的修正版。本迁移的 downgrade 仅恢复冻结的旧基础元数据及规则，保留额外运营约束、变量和全部版本，不恢复历史定制名称/说明，也不回滚正文或当前版本指针。若确需恢复旧协议，须另行审批配套元数据、正文发布与客户端回退，不可绕过校验。

若之后获准做真实生成质量验收，所有 Agent/E2E 请求必须携带 `X-Agent-Name: code-agent`、本次唯一的 `X-Agent-Run-Id` 和 `X-Test-Run-Id`，并核对费用来源。本次迁移定向 pytest 仅在隔离内存 SQLite 中通过 Alembic Operations 执行该 revision，并调用现有发布校验函数；不连接真实数据库、不调用外部模型。

## 5. 扩展问题对照表（可选加演）

| 业务方反馈                   | 改哪个 key                                                                                 | 怎么改                                                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 人物 MV 里空镜太多           | `ass.scene_shots.rules`                                                                    | 追加："人物镜是本片主体，空镜仅用于段落转场与情绪留白，不得为凑占比而连续安排空镜。"（占比数值区间由程序计算，提示词只调倾向）                    |
| ASS 人物变脸或没有按场景换装 | `ass.scene_plan.rules`、`storyboard_line.requirements`、`story_bible.ass.character_policy` | 面部身份与发型全片一致；`wardrobeByCharacter` 为每个大场景规划不同整套服装，逐镜提示词逐字执行本场服装并忽略参考图原始服装。                      |
| 通用 MV 没有高潮             | `general.story_outline.rules`                                                              | 强化叙事弧光条："高潮段落（约 60%–80% 进度处）必须切换为近景特写与快节奏镜头，与前段形成明显情绪落差。"                                           |
| 身份大头照不像本人           | `portrait.digital_human_ref`                                                               | 检查是否只上传一张身份参考图；保留面部、年龄、发型及儿童/卡通特征，不继承衣着职业背景。新版必含片段和存量 DB 发布要求见第 4 节。 |
| LLM 输出 JSON 失败率升高     | `common.pure_json_suffix`、各 `*.retry_user`                                               | 仅在此类故障时调整；正常运营不建议动解析兜底链路                                                                                                  |

不建议常规运营修改：`storyboard_line.system`（含版本标注行 `{{prompt_version}}` /
`{{schema_version}}`，保留可追溯线上输出所用版本）、`storyboard_line.repair.system`、
`chat.default_system`（与视频主线无关）。
