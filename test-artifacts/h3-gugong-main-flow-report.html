主流程设计

项目镜头→模型能力校验→按 provider 路由→模型执行池→RunningHub H3→TOS 视频 / 封面→镜头资产

可扩展调度

任务快照保存 provider、providerModelId、executionPool 与 executionConcurrency。H3 使用 runninghub-h3 / 2；不同模型使用独立池，互不占槽。

故障恢复

供应商 taskId 立即落库；服务重启或管理后台对账时按 provider 查询和恢复，避免把 H3 任务误查到 Seedance 接口。

资产一致性

RunningHub 临时输出转存 TOS，并抽取首帧封面与缩略图，最终沿用现有 ShotAsset 持久化链路。

踩坑与边界

最关键的坑：MiniMax H3 官方 Ref2VA 能支持最多 9 图、3 视频、3 音频，但“模型能力”不等于“当前托管工作流能力”。线上 RunningHub JSON 仍是旧版三图工作流，只有 3 个 LoadImage 槽和 ref_image_0/1/2，没有视频/音频节点。因此本次不能声称动作 MP4 和 WAV 已被模型参考。
  • “要求 6 张”不是最小数量约束：当前适配器 1 图、2 图均可成功；缺槽会复用最后一张图。
  • 主流程以当前真实能力注册为 1–3 图、0 视频、0 音频；升级工作流后只需调整 provider 适配和能力配置。
  • H3 结果自带 AAC 音轨，但这不代表支持用户提供的参考音频。
  • 线上 UI 浏览器验证停在登录页；为避免在浏览器自动化中重复传输管理密码，最终模型列表、提交、轮询、回存及 422 校验通过受控远程 API 完成。
